Deploy Doorman with MDM, without breaking the Mac.

Prepare, pilot, deploy, operate, update, and remove Doorman across a managed macOS fleet. The design is portable across capable Apple MDMs: one signed package, standard Apple profiles, per-device identity, staged rollout, and proof that traffic really works.

Start with the deployment sequence See daily IT operations
Managed deployment is a design preview, not a production-ready download.

The current macOS download is an interactive internal preview. Do not distribute the current generated MDM bundle: secure headless per-device enrollment (TIA-7685), signed release artifacts, trust validation, and real-tenant MDM tests must pass first. You can use this guide now to prepare Apple Business Manager, MDM groups, policies, network tests, and a pilot plan.

1 · Read this first

Know what is real, planned, and blocked.

An MDM saying “package installed” is not the same as a protected endpoint. Doorman only calls a Mac Protected after the required components and a recent end-to-end canary have passed.

Capability Status What IT should do
Interactive macOS preview Preview Use only on test Macs. It is not the managed enterprise package.
MDM fleet console concept Interactive demo Evaluate workflows and state definitions with sample data.
Secure zero-touch enrollment Blocked · TIA-7685 Do not ship an organization token in a profile, package, script, or plist.
Signed/notarized universal MDM package Planned Wait for a release explicitly labeled for managed deployment.
Certificate and proxy topology Phase-0 validation Inventory SWG, VPN, EDR, PAC, and existing proxy controls now.
Vendor support Validation pending Use Verified, Guided, and Unverified evidence per product/version/plan.
Never put these in fleet-wide artifacts.

A long-lived organization bearer token, a shared endpoint CA private key, provider API keys, or reusable device bootstrap secrets. A configuration profile should carry only non-secret desired state. Each Mac must obtain its own revocable identity.

2 · Pick the honest enrollment tier

“Zero-touch” applies to organization-owned ADE Macs.

Choose the tier before creating profiles. The available Apple payloads and the employee experience differ by enrollment type.

Tier A · Recommended

Automated Device Enrollment

Organization-owned, supervised Macs assigned through Apple Business Manager. Target experience: Doorman installs after enrollment with no employee setup or certificate prompt.

Tier B

Device Enrollment

A user completes the Mac’s MDM enrollment once. After that, the MDM can deliver the managed package and device-channel profiles. Describe this as “silent after enrollment,” not zero-touch.

Tier C

User Enrollment / BYOD

Privacy-preserving limited management. Default to tool-native gateway configuration. Do not promise a system extension or device-wide interception on a personally owned Mac.

Tier D

Unmanaged Mac

Use the interactive app and app-owned updater. macOS consent and trust prompts remain visible; Doorman must not try to bypass them.

3 · Prerequisites

Prepare Apple, Doorman, and the network.

Apple

Enrollment foundation

  • Apple Business Manager is linked to the MDM.
  • Test Macs are assigned to the correct MDM server.
  • ADE enrollment is confirmed on a wiped pilot Mac.
  • FileVault and standard-user behavior are represented.
Doorman

Organization decisions

  • Managed Visible or Managed Quiet is selected.
  • Support URL and escalation owner are defined.
  • Canary, early, and broad rollout groups exist.
  • Passthrough expiry and stale/offline thresholds are approved.
Network

Coexistence inventory

  • Corporate proxy, PAC, SWG, VPN, EDR, and DNS controls are listed.
  • Required gateway and release hosts are allowed.
  • Captive portal and off-network cases are in the test plan.
  • The original proxy state is recorded for safe restoration.
Use a real pilot, not only a lab VM.

Include Apple silicon and Intel where still supported, standard users, FileVault, sleep/wake, reboot, office and home networks, and the same security agents your employees actually run.

4 · Deployment bundle

Every capable MDM receives the same portable artifacts.

A vendor connector may automate upload and assignment later; it must not change the endpoint security model. Download only a release bundle explicitly marked MDM Verified for your vendor/version/plan.

Artifact Purpose Required evidence
Universal product-archive PKG Installs the app and its managed service for arm64 and x86_64. Developer ID signature, notarization, versioned receipt, SHA-256.
Managed preferences profile Non-secret org ID, gateway list, mode, policy channel, ring, and support URL. Schema version, precedence rules, required/optional field behavior.
Identity/trust profile ACME/SCEP or approved public trust material; no private CA key. Rotation, overlap, expiry, revocation, and offline behavior tested.
System extension profile Preapproves a signed extension only if the validated architecture uses one. Exact team ID, bundle ID, extension type, and supported enrollment tiers.
Managed login/background items Keeps the approved service available across reboot and login. Publisher and item identifiers match the signed release.
PPPC profile Grants only permissions proven necessary by the release. No broad speculative permissions.
Readiness check Reports installed, configured, reachable, conflict-free, and canary results. Redacted output; delivery receipt alone cannot return Protected.
Rollback/uninstall artifact Restores networking, revokes identity, and removes Doorman in safe order. Forced-failure and interrupted-removal tests pass.
Managed configuration is desired state, not a secret store.

It may identify the organization and gateways, but enrollment must exchange a one-use, device-bound challenge for a unique device credential. Unsupported required schema fields keep the last-known-good configuration and surface Attention; optional unknown fields are ignored and reported.

5 · Safe deployment sequence

Install trust before the app. Enable routing last.

Keep all pilot Macs in passthrough until observed state matches desired state and the end-to-end check succeeds.

  1. Enroll the Mac. Confirm ADE or Device Enrollment, supervision/management state, assigned user, MDM check-in, and the intended rollout group.
  2. Deliver device identity and public trust. Use the approved ACME/SCEP or one-use bootstrap design. Never install a shared endpoint signing private key.
  3. Deliver managed preferences. Set organization, gateways, endpoint visibility, fail-open policy, support URL, policy channel, and rollout ring. Keep credentials out of the profile.
  4. Preapprove only required Apple controls. Assign the release-matched system extension, PPPC, and background-item profiles. Preapproval does not install or activate the app by itself.
  5. Install the signed and notarized PKG. Pin the approved version and checksum. The service starts in passthrough and records the original network/proxy state.
  6. Complete per-device enrollment. Exchange a short-lived, device-bound challenge for a unique revocable identity stored with restrictive System Keychain access.
  7. Evaluate readiness. Verify package receipt and signature, config schema, identity, trust chain, service or extension, gateway reachability, foreign network controls, and a real canary request.
  8. Enable the route for the canary ring. Doorman may enforce only after all required checks pass. Pause automatically when crash, protection, network-conflict, or canary thresholds regress.
  9. Bake, then expand. Move from canary to early and broad groups only after the defined bake window. Keep a tested rollback release available throughout.

These states are deliberately separate. “Delivered,” “installed,” and Apple declarative management status are evidence, but only Doorman’s fresh end-to-end verification can produce Protected.

6 · MDM-specific setup

Map the same sequence into your MDM.

Product menus and plan capabilities change. Follow your vendor’s current documentation, record the exact product/version/plan tested, and treat the Doorman support label as evidence—not marketing shorthand.

Generic Apple MDM baseline
  1. Create canary, early, broad, and rollback scopes.
  2. Upload the signed PKG without repackaging it.
  3. Upload the release-matched identity/trust, managed preference, background item, and conditional extension/PPPC profiles.
  4. Assign profiles in the safe sequence, then the PKG, to the canary scope.
  5. Run the readiness inventory check and reconcile its result with the Doorman Devices view.
  6. Enable routing only for devices that are Ready; bake and expand by ring.

Minimum capability: ADE or Device Enrollment, signed custom PKG deployment, custom Apple configuration profiles, certificate payloads, managed background items, and device inventory/status. API automation is optional.

Jamf Pro
  1. Add the product-archive PKG to the approved distribution point.
  2. Create separate computer configuration profiles for trust/identity, managed preferences, background items, and any validated extension/PPPC payload.
  3. Use static or smart groups for canary, early, broad, Attention, and rollback populations.
  4. Deploy profiles before the installation policy. Use the release receipt and readiness extension attribute for detection.
  5. Do not infer Protected from policy logs or a package receipt; reconcile the Doorman canary timestamp.

Direct API automation is a candidate only after least-privilege credentials, package distribution, configuration profile behavior, rate limits, and the exact Jamf version are validated.

Microsoft Intune
  1. Add the signed installer as an unmanaged macOS PKG app and configure release-specific detection.
  2. Deploy Apple configuration profiles through the supported custom/settings catalog paths.
  3. Use Entra/Intune assignment groups for canary, early, broad, and rollback rings.
  4. Assign required profiles before the app; account for Intune reporting and check-in latency during bake decisions.
  5. Compare Intune installation status with Doorman readiness and canary evidence before expanding.

Confirm package structure and detection requirements against the current Intune documentation. “Installed” in Intune remains delivery evidence, not protection proof.

Kandji
  1. Add the signed PKG as a Custom App and define an auditable rule for installation state.
  2. Add each Apple profile as a Custom Profile, keeping identity/trust separate from policy.
  3. Map canary, early, broad, and rollback to Assignment Maps or Blueprints.
  4. Assign profiles first, then the Custom App. Keep the first cohort in passthrough until readiness passes.
  5. Display Kandji agent action state separately from Apple MDM state and Doorman protection state.

A connector is optional; the portable artifact path remains the security baseline.

Mosyle, Addigy, SimpleMDM, JumpCloud, Fleet, Workspace ONE, and others

Use the generic sequence with the vendor’s custom PKG, custom profile, assignment group/policy/blueprint, and inventory mechanisms. Until a named product/version/plan passes the complete real-tenant matrix, label it Guided or Unverified, never Verified.

  • Verified: full install, trust, readiness, update, rollback, uninstall, offline recovery, and status reconciliation passed in a real tenant on a recorded date.
  • Guided: official artifacts and mapped steps exist, but the full matrix has not passed.
  • Unverified: registry entry only; no compatibility promise.

7 · Certificates, proxy, VPN, and EDR

Unknown network topology means passthrough.

The endpoint must never leave macOS pointing at a dead local proxy. It must also never overwrite an existing corporate proxy, PAC, SWG, VPN, EDR network component, or Global HTTP Proxy without an explicitly validated coexistence mode.

Certificate rules

Unique, short-lived, revocable

  • Install public trust material through the MDM.
  • Use ACME/SCEP or a one-use device-bound bootstrap for identity.
  • Keep private keys out of packages, profiles, logs, and diagnostics.
  • Rotate with an overlap window; test expiry, revocation, reboot, and offline behavior.
  • If safe signing cannot be proved, use tool-native routing without interception.
Routing outcomes

Four explicit states

  • Supported: direct or validated owned route.
  • Chained: Doorman safely preserves and uses the corporate upstream proxy.
  • Passthrough-only: endpoint remains healthy but Doorman does not intercept.
  • Unsupported: do not enable the endpoint route; use cloud/tool-native deployment.
Offline expiry must preserve the network.

If a signer or device identity expires while a Mac cannot reach Doorman, the endpoint restores or preserves the original route and reports Stale/Attention. It must never keep interception active with invalid trust, report Protected, or block normal traffic.

8 · Pilot and production gates

Prove safe recovery before scaling.

Per-device readiness
  • Expected package receipt, code signature, notarization, and checksum.
  • Managed config schema is supported and effective values match policy.
  • Unique device identity and required trust chain are valid.
  • Service/extension is healthy after login, reboot, and sleep/wake.
  • Gateway and upstream AI provider are reachable.
  • Foreign proxy/VPN/security state maps to an approved outcome.
  • A recent end-to-end canary passed through the effective route.
Fleet GA gate
  • Every forced failure and uninstall test restores networking.
  • ADE pilot requires no employee setup interaction.
  • Artifact/log scans find no fleet bearer secret or shared CA private key.
  • Staged rollout halts automatically under injected regression.
  • Rollback succeeds from each supported release and macOS version.
  • Generic Apple MDM plus Jamf, Intune, Kandji, and one more real tenant pass.
  • RBAC, audit, privacy, accessibility, and incident runbooks are approved.

Test current supported macOS plus the next beta, Apple silicon and supported Intel, standard/admin users, FileVault, multiple users, login/logout/reboot, direct/PAC/proxy, VPN/EDR, captive portal, offline, gateway outage, package downgrade, profile removal, certificate rotation/expiry/revocation, and interrupted uninstall.

Status language

Protected has a deadline

Protected requires a fresh canary under the current policy. Protected—Passthrough is healthy but intentionally bypassed. Stale means proof is older than policy allows.

Remote actions

Typed and auditable only

Recheck, collect redacted diagnostics, enter/exit passthrough, rotate identity, quarantine, and prepare uninstall. No arbitrary remote shell. Every action is scoped, signed, expiring, replay-protected, and recorded.

10 · Updates, rollback, and uninstall

MDM owns the binary lifecycle on managed Macs.

Doorman owns readiness, safe route preparation, and actual-result reporting. It must not compete with the MDM’s package update or removal workflow.

Update by ring

  1. Verify release signature, notarization, checksum, schema, and rollback compatibility.
  2. Put eligible canary Macs into passthrough if the release requires route/service mutation.
  3. Assign the package and release-matched profiles through the MDM.
  4. Wait for installed, ready, and Protected as separate milestones.
  5. Honor bake gates before early and broad expansion.

When a desktop release is needed

Native macOS/API security changes, Electron/runtime security fixes, entitlements, installer/service changes, trust/key algorithm changes, a required managed-config capability, a new native traffic mechanism, incompatible telemetry, or a security incident requiring binary replacement.

New AI models/providers, pricing, routing policy, gateway failover order, certificate rotation, and existing policy fields are gateway/config changes—not desktop releases.

Safe removal order is not optional.
  1. Enter passthrough and restore the original network route.
  2. Verify normal network and AI-tool connectivity without Doorman enforcement.
  3. Revoke the device identity and any per-device signer.
  4. Use MDM to remove the app/service with the approved uninstall artifact.
  5. Remove Doorman profiles and public trust last.

If removal is interrupted, the endpoint remains or returns to passthrough. Profile removal must never strand a Mac behind an owned localhost proxy.

11 · Troubleshooting

Restore connectivity first, then repair protection.

Symptom Check Safe response
Package says installed, device is Provisioning Managed config, unique identity, service, gateway, canary, and profile assignment order. Keep passthrough; repair the missing prerequisite and recheck.
Certificate is untrusted or expiring MDM profile scope, chain, key usage, expiry window, last successful rotation. Rotate with overlap. If safe trust is unavailable, disable interception.
Gateway cannot be reached DNS, firewall, proxy authentication, captive portal, regional endpoint, system time. Restore/preserve original route and report Attention; never dead-end traffic.
Corporate proxy/PAC changed Desired versus observed proxy owner and the compatibility registry entry. Use validated chaining or passthrough/tool-native mode. Do not overwrite it.
VPN or EDR causes a conflict Exact products, versions, extension types, activation order, on/off network behavior. Move the affected scope to passthrough and use cloud/tool-native routing until validated.
Device is Stale but online Last heartbeat versus last verified, policy version, canary error, system sleep. Run a typed recheck; do not manually mark Protected.
Update stalls or regresses Ring, MDM delivery result, installed version, readiness, crash/network thresholds. Pause rollout, place the cohort in passthrough, and assign the tested rollback release.
Uninstall is incomplete Original route restored, identity revoked, app receipt, service, profiles, trust. Finish the ordered workflow; networking must be restored before trust removal.
Diagnostics are redacted by default.

Collect versions, timestamps, policy/config hashes, certificate fingerprints and expiry, route ownership, reachability, and normalized errors. Do not collect prompts, response content, provider keys, private keys, raw bearer tokens, or full personal network history in routine endpoint diagnostics.

12 · Security and privacy contract

Managed and quiet never means covert.

Required controls

  • Per-device, revocable identity with bounded lifetime.
  • Least-privilege, write-only encrypted MDM connector credentials.
  • Typed, allowlisted, signed, expiring, replay-protected remote actions.
  • Organization isolation, RBAC, destructive-action confirmation, and audit.
  • Desired, delivered, observed, and effective state stored separately.
  • Fail-open behavior with bounded, visible passthrough ownership.

Explicit non-goals

  • No stealth install on unmanaged or personal Macs.
  • No bypass of Apple consent outside supervised/MDM-authorized controls.
  • No arbitrary remote shell or hidden employee surveillance.
  • No routine prompt/content capture in health telemetry.
  • No claim that every MDM exposes the same API or capability.
  • No new desktop build merely to recognize a new AI model.
